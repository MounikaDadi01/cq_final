Verified the two root causes against the source. Here's the review.

## Why the run reported "deploy published" when it wasn't

This is the most serious one, and it's the reason you saw contradictory output — the agent printed *"Partial deployment only… Outcome: unverified"* and the launcher printed *"── deploy published"*.

[launch-deploy.ts:314-315](eval/scripts/launch-deploy.ts#L314-L315) recomputes status from scratch and PATCHes it unconditionally:

```ts
const evidenced = recordings.length > 0 && Boolean(current?.verified_url)
const status = exitReason === 'completed' ? (evidenced ? 'published' : 'unverified') : 'failed'
```

Three things go wrong together:

- **The agent's own verdict is discarded.** `current.status` is selected on [line 306](eval/scripts/launch-deploy.ts#L306) and never read. The agent catches its own errors, so the sandbox always exits 0 → `exitReason === 'completed'`. A stopped deploy that read *any* url off the page gets relabelled `published`, and the blocker note is overwritten with `'recording saved and url read back'`.
- **The evidence isn't scoped to this run.** Recordings are queried by `revision_id` only, unordered, and `verified_url` is never cleared at launch. Note that your two runs printed the *same* recording hash (`page@46391fba…`) in the summary line while the run itself saved `page@cbeca34…` and `page@472b71d0…` — that's this bug, visible. `recording_artifact_id: recordings[0]?.id` is grabbing an arbitrary prior run's recording.
- **The RESULT.json compounds it.** [agent.deploy.ts:576](sandbox/agent.deploy.ts#L576) sets `published:` to `artifacts.map(...)` — the *download* list, not what was confirmed. So a stopped run files a report listing all three canvases as published. And [agent.deploy.ts:454](sandbox/agent.deploy.ts#L454) declares `outcomeReported`, reads it at line 581, but **never assigns it** — every RESULT.json falls through to the "agent never reported an outcome" default, even when it did.

## Why COPY_MAPPING_MISSING stopped run 4

[launch-deploy.ts:149](eval/scripts/launch-deploy.ts#L149):

```ts
const REQUIRED_TOOL_FIELDS = ['Ad name', 'Audience', 'Placements', 'Daily budget', 'Call to action']
```

That mirrors the five fields the Deploy screen collects — but Adstream's **Primary text** is in neither the deployment row nor this preflight. Meanwhile [agent.deploy.ts:508](sandbox/agent.deploy.ts#L508) hands the box `Copy available: {"eyebrow":…,"headline":…,"body":…}` with no composition rule, while the skill correctly forbids inventing one. So the agent did the right thing and stopped — but the comment above the list promises every such stop is "knowable from the deployment row, so it is knowable now," and the one field that actually blocked you isn't covered.

Worth noting run 3 got past this by inventing `primary_text = "testing the rendering"` — same missing contract, opposite (and worse) failure.

## Why portrait's Publish stayed disabled

Confirmed contributing factor: [agent.deploy.ts:247](sandbox/agent.deploy.ts#L247) waits a flat `await p.waitForTimeout(400)` after every action, including a 1.7MB `setInputFiles`, with no wait-for-enabled or upload-complete check. Landscape (1.05MB) cleared it; portrait (1.7MB, the largest) didn't. That's a hypothesis about Adstream's behavior, not something I can confirm from this repo — but the missing readiness gate is real regardless.

Related: [launch-deploy.ts:112](eval/scripts/launch-deploy.ts#L112) — publish entries carry no `bytes`/digest, so the skill's "byte count matches the manifest" stop condition is unimplementable, and nothing checks the 10MB ceiling before spending a sandbox.

## Other bugs found

- [agent.deploy.ts:242](sandbox/agent.deploy.ts#L242) — `upload` falls back to `artifacts[0]` when the canvas name doesn't match, silently publishing the wrong creative.
- [agent.deploy.ts:506](sandbox/agent.deploy.ts#L506) — instructions tell the agent to name every canvas `hydration.campaign.name`, but `listConfirmed` is a `Set` of names compared against `publish.length`. An obedient agent publishing 3 canvases gets `Set.size === 1` and is always downgraded to unverified. Your runs dodged this because the model appended `(landscape)` on its own.
- [launch-deploy.ts:125](eval/scripts/launch-deploy.ts#L125) — run/deploy_run rows are inserted *before* the preflight `process.exit(1)`, leaving orphan `starting` rows.
- [launch-deploy.ts:84](eval/scripts/launch-deploy.ts#L84) / [:96](eval/scripts/launch-deploy.ts#L96) — only `revisions[0]` ships from a multi-revision deployment (unordered `in.()`), and canvases with no matching artifact are dropped silently.
- [agent.deploy.ts:336](sandbox/agent.deploy.ts#L336) — `confirm_in_list` navigates to a model-supplied URL with no same-host guard (unlike `act` has), and confirms by substring, so a prefix name can credit two confirms to one row.
- [launch-deploy.ts:302](eval/scripts/launch-deploy.ts#L302) — a throw from any `rest()` in the `finally` skips `sandbox.kill()`, leaking the box and masking the original error.

- Each ad's detail page gets read for its image before the run can claim `published` — which is where a silently dropped upload actually surfaces, and the case your skill already describes.

# How the two boxes are hydrated

## The shape of a hydration file

Both boxes get exactly one `/home/user/hydration.json`, written by the launcher. It's a **manifest, not a payload** — it says what should be in the box, where each thing comes from, what order to read it in, and what was deliberately left out. [`eval/src/hydration.ts`](eval/src/hydration.ts).

The five properties it's built around are worth memorising, because they're each an answer to a specific disqualifier:

| Property | Why it exists |
|---|---|
| Nothing names a customer | every brand value arrives as data resolved from a kit id, so a third brand is a data problem |
| The skill is mounted, not inlined | `SKILL.md` goes in as the same bytes a developer invokes locally — paraphrasing it into a prompt would make two sources of truth |
| Ordering is declared | "whatever order the code happened to read things in" is the hardcoded ordering that's disqualifying |
| Context travels with the job | prior conversation, resolved brand values, known findings, the parent's tree |
| What's withheld is stated | the negative space is the interesting half of an isolation claim |

## The generation box

`hydration.mounts[]` lists every file with a `path`, a `storageKey`, and a `digest`. Then — and this is the part I'd lead with — **the box fetches its own files.** [`agent.generate.ts:85`](sandbox/agent.generate.ts#L85), `pullMounts()`: for each mount it GETs `brains/<storageKey>` using `CQ_RUN_TOKEN`, verifies the sha256 where the manifest states one, and writes it to disk.

The launcher could have pushed those bytes in. It didn't, for a reason worth saying out loud:

> If the launcher pushes, the run never exercises the policy that's supposed to protect the tenant. A leak would sit undetected because nothing ever asked the database for anything. Fetching here makes **every run a live test of its own isolation** — if the token is wrong or the policy is wrong, hydration fails loudly instead of quietly working.

Three lifetimes, and they're the answer to "a rebrand can't need a rebuild":

- **`baked`** — `SKILL.md`, the toolkit. In the image, identical every run.
- **`kit`** — `DESIGN.md`, `README.md`, `brand/asset_manifest.json`, every asset, every shipped font. Pulled fresh per run from `brains/<kit-id>/`.
- **`job`** — the request, its copy, canvases, open comments, and on an edit the parent revision's tree.

The brand is `kit`, so a rebrand is new bytes in a bucket. Nothing rebuilds.

**What's withheld, and why it's the good answer:** `tokens.json` is a cache that disagrees with `DESIGN.md` *and is newer than it* — so anything resolving by recency picks the wrong value three times over. It is never hydrated, and `hydration.withheld[]` records that with the reason. The safest way to not consult a file is for it not to be in the box.

## The deploy box

Same file, different contents — and the differences are all consequences of what a deploy is.

`publish[]` carries `{ canvas, relative_path, signed_url, bytes, width, height }`. The box downloads each one **before the browser opens** ([`agent.deploy.ts:105`](sandbox/agent.deploy.ts#L105)) and checks the byte count against the manifest, because an artifact that won't download is a blocker at the cheapest possible moment — before anything exists in someone else's account. A truncated fetch gives you a valid PNG header and a short file, which uploads without complaint and renders as a half-drawn ad.

Three deliberate differences from generation:

1. **No brain at all.** `withheld` says it plainly: *"a deploy publishes finished artifacts and has no reason to open a logo or a font; the deploy role is granted nothing on `brand_assets` or `brand_fonts`."*
2. **Credentials by name, never by value.** `credential_env: ['DEPLOY_USERNAME', 'DEPLOY_PASSWORD']` — the *names* of variables. The secrets sit on the sandbox environment. The hydration file is saved beside the run for audit, and anything in it is readable forever. The launcher enforces this three ways: value-scans the high-entropy secrets, structurally checks the credential fields hold variable names, and rejects any field that looks like it holds a password.
3. **It reads from `work/`, not `brains/`** — and it uses pre-signed URLs rather than its own token.

**Expect him to ask about that third one.** The honest answer: generation asks the database and lets policy decide, which is the stronger demonstration; deploy is handed exactly N pre-authorised URLs, which is the tighter grant. Signed with the same budget as the sandbox timeout so nothing expires mid-run. Both are defensible, they're not symmetric, and generation's is the one to point at when he asks how you know isolation works.

# How work gets out

**`save_work` is the only path out of a box.** [`sandbox/save_work.mjs`](sandbox/save_work.mjs). No backend fetch, no volume mount, no scp, no supervisor copying the directory afterwards. If it doesn't run, the work doesn't exist anywhere else.

It's dependency-free and a plain executable on purpose: a developer can open a shell in a live box and read it top to bottom to see exactly what leaves and where it goes. A compiled SDK call can't be read that way.

## Hydration

**The deploy box** gets the same file with different contents: pre-signed URLs to the finished renders in `work/`, each with its byte count, downloaded and checked *before the browser opens* — because an artifact that won't download is a blocker at the cheapest possible moment, before anything exists in someone else's account. ## Saving, and the interruption

`save_work` is the only path out of a box. Nothing reaches in.

The whole durability story is one ordering:

> **Bytes first, row second.** An object with no row is an orphan — invisible, harmless, cleanable. A row with no bytes is a lie the rest of the system believes, and something downstream will try to publish it.

**So what happens if it dies between the two?** You get an orphaned object. Nothing references it, nothing breaks, and the retry recovers it: the upload comes back **409 already exists**, `save_work` falls through and inserts the row. The failure it's guarding against is precisely that gap.

And it's **append-only, not an upsert** — deliberately. Overwriting needs `UPDATE` on `storage.objects` and the run role doesn't have it, so a box cannot rewrite what it has already saved. That fights with wanting safe retries, and append-only wins, because the 409 path *is* the safe retry.

Four more things that make an interruption survivable:

- **`partial` is set before the first byte moves**, so a box that dies mid-save is already labelled as having incomplete work rather than looking untouched.
- **A re-run adds rather than duplicates** — it asks the database what this revision already holds and skips it.
- **The acknowledgement comes from the returned row, not a 2xx.** A write that returns no row hasn't been read by anyone, and "the request succeeded" is a weaker claim than "the row is there."
- **`--final` is a request, not an instruction.** If any file failed, it refuses to mark the revision complete — a revision marked complete with missing artifacts would get published.

One file failing never abandons the rest; nine of ten renders saved is worth far more than stopping at the first refusal, and the failures become a blocker finding.

And with the change you just pushed, the run's own account now flushes every thirty seconds — so a box killed mid-form leaves a transcript behind instead of nothing.

**If he pushes on what's missing:** work survives, billing doesn't. The agent isn't handed the list of artifacts that already exist, so a resumed run can regenerate an image it already paid for. `save_work` then declines to overwrite it — the record stays correct, the spend already happened. It's the first item in DECISIONS.md's "what I'd do next," and the launcher already queries that list, so it's a matter of passing it into hydration.

# What the transcript does

**The problem it solves:** a box is deleted the moment its run ends, and an unannounced kill gives it no chance to write anything on the way out. So a transcript assembled in memory and written at the end is *precisely the transcript you don't have when you need it* — because the runs worth reading are the ones that died.

Before this, `steps` only reached storage inside `RESULT.json` at the very end. The maxTurns run that died mid-third-ad left nothing behind.

**So it flushes on a timer** — every thirty seconds — and whatever has been flushed is already durable.

Two design details carry the reasoning, and both are good answers if he probes:

**Numbered segments, not one growing file.** `save_work` is append-only by design: a path it has already stored comes back 409 and is skipped, which is exactly what stops a box rewriting its own history. So a single `transcript.jsonl` re-saved every thirty seconds would persist its first thirty seconds and **silently discard everything after**. Segments — `transcript/<run>-000.jsonl`, `-001.jsonl` — each get saved exactly once, and reading them in filename order reconstructs the run.

**The flush is scoped: `save_work --only transcript`.** A bare `save_work` would sweep up anything else new in the tree, and a PNG caught half-written would be stored and filed as a finished `render`. Append-only means that row could never be corrected. *The debugging tool must not be able to publish a corrupt ad.* Making renders durable as they appear is worth doing — it's a different change with its own failure modes, and it doesn't get to ride in on this one.

**Three smaller things:**

- Segments land as role `result`, which isn't incidental — the deploy role may only insert `recording` and `result`, so any other role would be refused by policy on the deploy box. And `result` is what they are: the box's own account of its work.
- Secrets are scrubbed **by key name**, not by content — `pass|secret|token|key|credential|authorization`. Signed URLs keep their path and lose their query, because knowing *which* artifact was fetched is most of the value of the line.
- **`line()` can never throw.** A transcript that breaks the run it's describing is worse than no transcript, and this is the one component whose failure must not cost a render that has already been paid for. Same at flush: a failure is logged and dropped, because a box that can't save its transcript can still finish its work and save that.

**The distinction worth stating out loud:** this is not a substitute for findings. A finding is a claim a person should act on. The transcript is evidence for whoever is debugging, and nothing in the product reads it back.
