Verified the two root causes against the source. Here's the review.

## Why the run reported "deploy published" when it wasn't

This is the most serious one, and it's the reason you saw contradictory output — the agent printed *"Partial deployment only… Outcome: unverified"* and the launcher printed *"── deploy published"*.

[launch-deploy.ts:314-315](eval/scripts/launch-deploy.ts#L314-L315) recomputes status from scratch and PATCHes it unconditionally:

```ts
const evidenced = recordings.length > 0 && Boolean(current?.verified_url)
const status = exitReason === 'completed' ? (evidenced ? 'published' : 'unverified') : 'failed'
```

Three things go wrong together:

- **The agent's own verdict is discarded.** `current.status` is selected on [line 306](eval/scripts/launch-deploy.ts#L306) and never read. The agent catches its own errors, so the sandbox always exits 0 → `exitReason === 'completed'`. A stopped deploy that read *any* url off the page gets relabelled `published`, and the blocker note is overwritten with `'recording saved and url read back'`.
- **The evidence isn't scoped to this run.** Recordings are queried by `revision_id` only, unordered, and `verified_url` is never cleared at launch. Note that your two runs printed the *same* recording hash (`page@46391fba…`) in the summary line while the run itself saved `page@cbeca34…` and `page@472b71d0…` — that's this bug, visible. `recording_artifact_id: recordings[0]?.id` is grabbing an arbitrary prior run's recording.
- **The RESULT.json compounds it.** [agent.deploy.ts:576](sandbox/agent.deploy.ts#L576) sets `published:` to `artifacts.map(...)` — the *download* list, not what was confirmed. So a stopped run files a report listing all three canvases as published. And [agent.deploy.ts:454](sandbox/agent.deploy.ts#L454) declares `outcomeReported`, reads it at line 581, but **never assigns it** — every RESULT.json falls through to the "agent never reported an outcome" default, even when it did.

## Why COPY_MAPPING_MISSING stopped run 4

[launch-deploy.ts:149](eval/scripts/launch-deploy.ts#L149):

```ts
const REQUIRED_TOOL_FIELDS = ['Ad name', 'Audience', 'Placements', 'Daily budget', 'Call to action']
```

That mirrors the five fields the Deploy screen collects — but Adstream's **Primary text** is in neither the deployment row nor this preflight. Meanwhile [agent.deploy.ts:508](sandbox/agent.deploy.ts#L508) hands the box `Copy available: {"eyebrow":…,"headline":…,"body":…}` with no composition rule, while the skill correctly forbids inventing one. So the agent did the right thing and stopped — but the comment above the list promises every such stop is "knowable from the deployment row, so it is knowable now," and the one field that actually blocked you isn't covered.

Worth noting run 3 got past this by inventing `primary_text = "testing the rendering"` — same missing contract, opposite (and worse) failure.

## Why portrait's Publish stayed disabled

Confirmed contributing factor: [agent.deploy.ts:247](sandbox/agent.deploy.ts#L247) waits a flat `await p.waitForTimeout(400)` after every action, including a 1.7MB `setInputFiles`, with no wait-for-enabled or upload-complete check. Landscape (1.05MB) cleared it; portrait (1.7MB, the largest) didn't. That's a hypothesis about Adstream's behavior, not something I can confirm from this repo — but the missing readiness gate is real regardless.

Related: [launch-deploy.ts:112](eval/scripts/launch-deploy.ts#L112) — publish entries carry no `bytes`/digest, so the skill's "byte count matches the manifest" stop condition is unimplementable, and nothing checks the 10MB ceiling before spending a sandbox.

## Other bugs found

- [agent.deploy.ts:242](sandbox/agent.deploy.ts#L242) — `upload` falls back to `artifacts[0]` when the canvas name doesn't match, silently publishing the wrong creative.
- [agent.deploy.ts:506](sandbox/agent.deploy.ts#L506) — instructions tell the agent to name every canvas `hydration.campaign.name`, but `listConfirmed` is a `Set` of names compared against `publish.length`. An obedient agent publishing 3 canvases gets `Set.size === 1` and is always downgraded to unverified. Your runs dodged this because the model appended `(landscape)` on its own.
- [launch-deploy.ts:125](eval/scripts/launch-deploy.ts#L125) — run/deploy_run rows are inserted *before* the preflight `process.exit(1)`, leaving orphan `starting` rows.
- [launch-deploy.ts:84](eval/scripts/launch-deploy.ts#L84) / [:96](eval/scripts/launch-deploy.ts#L96) — only `revisions[0]` ships from a multi-revision deployment (unordered `in.()`), and canvases with no matching artifact are dropped silently.
- [agent.deploy.ts:336](sandbox/agent.deploy.ts#L336) — `confirm_in_list` navigates to a model-supplied URL with no same-host guard (unlike `act` has), and confirms by substring, so a prefix name can credit two confirms to one row.
- [launch-deploy.ts:302](eval/scripts/launch-deploy.ts#L302) — a throw from any `rest()` in the `finally` skips `sandbox.kill()`, leaking the box and masking the original error.

- Each ad's detail page gets read for its image before the run can claim `published` — which is where a silently dropped upload actually surfaces, and the case your skill already describes.
